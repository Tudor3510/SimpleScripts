# PDF.js 6.2.108 Modifications

These instructions apply to the released, pre-built/compiled version of **PDF.js 6.2.108**.

## Allow cross-origin PDF URLs

The generic PDF.js viewer normally validates the URL supplied through the viewer and rejects a PDF URL whose origin differs from the viewer origin. To allow the viewer to attempt to load PDF files from other origins, modify the `validateFileURL` function in `web/viewer.mjs`.

> **Important:** Removing or changing this viewer-side origin check does not bypass browser security. The server hosting the PDF must still permit the request through CORS. For example, it may return an appropriate `Access-Control-Allow-Origin` response header. Your page's Content Security Policy (CSP), if present, must also permit the connection.

### Modification

1. Open the released PDF.js 6.2.108 file:

   ```text
   web/viewer.mjs
   ```

2. Locate the `validateFileURL` function. In the PDF.js 6.2.108 build used for these instructions, it is around **line 20257**.

3. Inside `validateFileURL`, locate the check that compares the PDF file's origin with the viewer's origin and throws an error when they differ.

4. Modify the function so that URLs from different origins are accepted instead of being rejected solely because `fileOrigin !== viewerOrigin`.

5. Save `viewer.mjs` and serve the modified file with the rest of the matching PDF.js 6.2.108 release files.

### CORS requirement

Allowing a foreign URL through `validateFileURL` only removes the generic viewer's own origin restriction. It does **not** grant PDF.js permission to bypass the browser's same-origin policy.

For a PDF such as:

```text
https://other.example/document.pdf
```

to be loaded by a viewer hosted on another origin, the PDF server must provide suitable CORS response headers. Otherwise, the browser can still block the PDF request.

## Open a hardcoded Base64 PDF

If you want the viewer to open a PDF that is hardcoded as Base64 data instead of loading the default PDF URL, modify the `async run` function in `web/viewer.mjs`.

1. Open:

   ```text
   web/viewer.mjs
   ```

2. Locate the `async run` function. In the PDF.js 6.2.108 build used for these instructions, the relevant code is around **line 19168**, immediately before the normal file-opening logic.

3. Decode your hardcoded Base64 PDF into binary PDF data, preferably a `Uint8Array`. If the Base64 value contains whitespace or line breaks, remove them before decoding. If it is a complete Data URL such as `data:application/pdf;base64,...`, remove the Data URL prefix first.

4. Before the existing code opens the configured/default file, call the viewer's `open` method with the decoded PDF data and a filename:

   ```js
   this.open(data, filename);
   ```

   Here, `data` is the decoded PDF data (for example, a `Uint8Array`) and `filename` is the filename that should be associated with the document, such as `document.pdf`.

5. Make sure the normal file-opening path does not subsequently open the default URL and replace the hardcoded document. Return from the relevant branch after the hardcoded PDF has been opened, or otherwise structure the logic so that only one document is opened.

This approach supplies the PDF directly from memory, so the PDF itself does not need to be fetched from a URL. Other PDF.js resources, such as the worker, fonts, CMaps, localization files, or WASM resources, may still be loaded separately when required.

## `file://` viewer pages and fake workers in Chromium

If you split PDF.js so that the main viewer is opened locally as a `file:///` HTML page in a Chromium-based browser while the remaining PDF.js resources are fetched from a hosted server, PDF.js can fall back to using a **fake worker** instead of a real Web Worker.

The reason is that a page loaded from `file://` has an opaque origin in Chromium. When PDF.js creates the module worker through a Blob URL, Chromium associates that Blob URL with the page's opaque origin, producing a URL such as:

```text
blob:null/...
```

Chromium rejects the corresponding **module** Web Worker in this situation. As a result, PDF.js cannot start its normal worker and falls back to its fake-worker implementation.

This behavior is specific to module Blob workers in this setup. **Classic Blob workers can work, while module Blob workers do not.**

Therefore, if you want PDF.js to use its normal worker in Chromium, avoid opening the viewer itself from `file:///` while depending on remotely hosted worker resources. Serve the viewer over `http://` or `https://` so that the page has a normal origin.
